# 渲染：为什么慢，怎么省时间

## 为什么慢

Remotion 的每一帧都是让无头 Chrome 把网页画出来再截图，交给 ffmpeg 编码。30 fps 的视频，一秒要截 30 张。全屏模糊、大阴影、大尺寸原图、3D 场景，每帧都要重新算一遍。

我们的实测（M1 Max，10 核，64 GB，并发 6，PNG 帧，crf 18）：

| 项目 | 数字 |
| --- | --- |
| 平均 | 1 分钟成片约渲 1.6 分钟 |
| 9 集合计 38.6 分钟 | 从头渲一遍约 62 分钟 |
| 画面动画多的集 | 接近 1.7 分钟每分钟 |
| 画面简单的集 | 约 1.3 分钟每分钟 |
| 速度 | 大约每秒 16–18 帧，比播放速度慢一半 |

## 有效的办法

按收益排：

1. **只重渲改过的集。** 渲染脚本接受集名，其余集直接用上次的文件。3 集大约 20 分钟，不用每次等 1.5 小时。
2. **合集不要整条重画。** 合集和分集只差一条全系列进度条。做法：
   - 分集照常渲，合集直接拼接渲好的分集；
   - 进度条单独渲成一条透明视频（ProRes 4444），每 3 帧只渲 1 帧，它每帧只移动约 0.1 像素，看不出来；
   - 用 ffmpeg 把进度条叠到底部；
   - 全屏场景前后，分集自己的进度条正在淡入淡出，盖不干净，这几段用合集的真实渲染补进去；
   - 进度条只取决于各集时长，时长不变就复用。

   合集从约 70 分钟降到 5–9 分钟，只改画面、不改时长时约 4 分钟。拿真实渲染逐帧比过，帧数一致。
3. **重的画面换成图片。** 片尾的封面墙原来是 8 张封面实时渲染再缩小，改成读导出好的封面图，这一集从 6.1 分钟降到 4 分钟。
4. **小样先行。** 审片时只渲关键帧和几秒短片段，确认了再全量渲。

模板里的 `pnpm compilation` 是最简单的版本：把 finalize 过的分集直接拼接。要做全系列进度条，按上面的叠加法扩展。

## 没用的办法

- **截图改 JPEG。** 我们实测没有提速，瓶颈在画面计算。还有副作用：成片会变成全范围色彩的 `yuvj420p`，一些播放器打不开或者发灰，上传也可能偏色。模板固定用 PNG 帧、BT.709、`yuv420p`（见 `remotion.config.ts`）。
- **并发从 6 调到 8。** 同样约 37 帧每秒。内存吃紧时反而更容易让渲染浏览器崩溃。
- **缩小模糊背景。** 没有明显变化。

## 稳定性

- **一次只跑一个渲染。** 两个渲染同时打包会抢同一个缓存目录。多个会话并行时，谁要渲染先说一声。
- **看内存。** 64 GB 的机器上，渲染加上几个本地 TTS 模型把内存吃满过一次，机器直接重启。渲染前看一眼 `vm_stat`，本地模型一次只加载一个。
- **渲染浏览器偶尔会崩。** Remotion 会自动换一个浏览器重试；反复崩就调低并发。
- **先渲到暂存目录。** 渲完、归一、检查都通过，再替换正式文件，旧文件留备份。

## 检查

```sh
pnpm finalize ep1 ep2     # 两遍 loudnorm：-15 LUFS / -1 dBTP，视频流直接复制
pnpm delivery-check       # 帧数、分辨率、帧率、编码、像素格式、色彩、音频、音画时长差、完整解码
```

检查通过只说明文件没问题。好不好看、好不好听，还要人从头看一遍、听一遍。

## 两个工程坑

- **TypeScript 7 和 Remotion。** Remotion 的 esbuild-loader 通过 `typescript.sys` 读 tsconfig，TypeScript 7 没有这个接口，JSX 会悄悄退回旧的 `React.createElement` 写法。`webpack-override.ts` 里把 loader 的 `jsx` 强制成 `automatic`。
- **字体。** 字幕用的中文字体要在渲染机器上装好（macOS 自带苹方）。在线加载 Google Fonts 时，每个渲染标签页都要下载上百个子集，网络慢时会超时，正式渲染建议用本地字体文件。
